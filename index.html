04

핵심 강점

여섯 축으로 정리했습니다. 각 항목의 구현 내용은 프로젝트 상세와 문제 해결 사례 탭에 있습니다.

라이브 안정성 · 데이터 정합성

  • 서버 간 보상 트랜잭션 — 개인 재화(Zone)와 길드 재화(World)가 분산된 구조에서 "타 서버 처리는 항상 성공한다"는 가정을 제거하고, 타 서버 검증 실패 시 앞서 차감한 재화를 복구하는 보상 트랜잭션 구성
  • 중복 요청 선차단 — 서버 간 처리 순서를 역전시켜, 계정 데이터를 관리하는 서버가 메모리에서 중복 요청을 먼저 막고 DB 저장에 성공한 요청만 플레이 서버에 반영
  • 운송 아이템 미도착 장애 해결 — 서버 마차 AI에 의존하던 도착 처리를 시간 기반으로 바꿔 미도착 경로 자체를 제거, 연출은 클라이언트에서 유지

성능 병목 개선

  • 이벤트 미션 DB 병목 — SP 사용량 급증 제보 → 로그 분석으로 원인 특정 → 메모리 캐싱 + TVP 일괄 저장. 저장 임계값을 CONFIG로 분리해 코드 수정 없이 N건당 1회 저장으로 조정 가능
  • 다중 강화 UI Reload 수백 회 → 1회 — ACK마다 Reload가 발생하는 구조에서 누적 수백 회 Reload가 클라이언트 렉으로 이어진 문제를 단일 Task + TVP 저장으로 해소

서버 아키텍처

  • 분산 World/Zone/공용 서버 — 서버 간 데이터 처리, 보상 트랜잭션, 멱등성 검증, 계층별 책임 분리(World 관리 · Zone 적용)
  • 인스턴스 서버 구조 설계 — 채널 방식 단일 월드에서 혼잡 지역만 인스턴스로 다중화. 서버 간 캐릭터 이동, 복귀 처리, 메모리 기반 운영 규모 산정
  • 시드 기반 데이터 재현 — 개인화 데이터를 전송하지 않고 서버·클라이언트가 동일 시드로 재현해 네트워크 전송량 제거

운영툴 · 개발 생산성

  • 운영툴 3명 체제 → 1인 전담으로 범위 확대 — 아키에이지 워에서 메인 3명 중 1명, 더 큐브에서는 기반 구조부터 전체를 혼자 설계·개발
  • 개발툴 — 대미지 분석 툴, 섹터 복사 툴, 연출 카메라·시퀀스 툴, 번역 툴, 아이템 설정 툴. 모두 타 직군이 개발팀 지원 없이 일할 수 있게 만든 도구
  • CI/CD AI 자동화 — Jenkins·Rundeck·Jira·Confluence를 API로 연동해 분석·관리를 자동화하고 반복 확인에 쓰던 시간 단축

글로벌 서비스

  • 다국어 우편 구조 문제 발견·제안·설득 — 유저 언어 정보가 별도 DB에만 있어 미접속 유저에게 우편 발급이 불가능한 구조적 문제를 직접 발견하고, 번역을 클라이언트에 위임하는 구조를 제안해 기획팀 설득 후 적용

핵심 작업

  • 분산 서버 간 보상 트랜잭션 — RAII 기반 롤백

    개인 재화와 길드 재화가 서로 다른 서버에서 관리되는 구조여서, 재화 소비를 단순 Fire-and-Forget으로 처리할 수 없었습니다. 개인 재화를 먼저 차감한 뒤 다른 서버에서 길드 재화 잔액을 검증해야 했고, 검증 실패 시 이미 차감된 상태를 되돌리는 경로가 필요했습니다. 메모리 검증 → 조건부 DB 커밋 → 실패 시 타 서버 롤백으로 이어지는 보상 트랜잭션으로 구성하고, 롤백을 RAII로 자동 처리해 어느 실패 경로에서도 누락 없이 실행되도록 설계했습니다. 예외나 조기 반환이 있어도 복구가 누락되지 않아, 실패 처리를 호출자의 기억에 맡기지 않는 구조입니다.

  • 중복 요청 선차단으로 출석 보상 중복 지급 방지

    일일 출석 보상은 Zone에서 보상을 처리한 뒤 World에 DB 저장을 요청하는 순서였기 때문에, 비동기 처리 중 동일 요청이 연속 유입되면 중복 지급이 가능했습니다. 처리 순서를 역전시켜 계정 단위 데이터를 관리하는 World가 메모리 카운트로 중복 요청을 먼저 차단하고, DB 저장 성공을 확인한 요청만 Zone에 통보해 보상을 반영하도록 변경해, DB 결과와 게임 서버 메모리 상태를 일치시키고 재시도 가능한 요청 구조를 확보했습니다.

  • 이벤트 미션 DB 병목 개선 — SP 호출 N건당 1회로 축소

    SP 사용량 급증 제보를 받고 로그를 분석해 이벤트 미션 처리가 원인임을 확인했습니다. 몬스터 1마리 처치마다 Task 1건을 DB에 저장하던 구조를 메모리 캐싱 후 TVP 일괄 저장으로 전환했고, 저장 임계값을 CONFIG로 분리해 코드 수정 없이 N건당 1회 저장으로 조정할 수 있게 구성했습니다(예: 1000 설정 시 1000건당 1회). 기준 건수 도달 또는 캐릭터의 Zone 서버 이동 시 flush하도록 해 서버 이동에 따른 진행도 유실도 함께 방지했습니다.

  • 다중 강화 응답 구조 개선 — UI Reload 수백 회 → 1회

    기존 구조는 Task 1건당 ACK 패킷이 1회 내려가고 ACK마다 UI Reload가 발생했습니다. 다중 강화는 1회 요청에 수십 회(예: 40회) 강화가 수행되고 성공 확률에 따라 시도가 더 늘어나 누적 수백 회의 Reload가 클라이언트 렉으로 이어졌습니다. N회 순차 처리를 단일 Task 일괄 처리로 바꾸고 결과 배열을 TVP로 일괄 저장해 DB 호출·클라이언트 응답·UI Reload를 각각 1회로 축소했습니다.

  • 우편 시스템 전담 및 글로벌 다국어 구조 개선

    계정·캐릭터·길드·시스템·보상·일반 우편 로직이 혼재된 코드를 소유 단위와 목적에 따라 전면 리팩토링하고, 전 서버 계정당 1회 수령 우편·주기 지급·다중 아이템 첨부를 신규 개발했습니다. 전체 유저 대상 우편은 계정별 사전 생성 대신 접속 시점 확인 방식으로 처리해 대량 DB 쓰기를 방지했습니다. 또한 유저 언어 정보가 계정 DB에만 존재해 미접속 유저에게 우편을 발급할 수 없는 구조적 문제를 직접 발견하고, 번역 텍스트 대신 CMS 키만 저장해 번역을 클라이언트에 위임하는 구조를 제안·설득해 신규 우편 타입으로 적용했습니다.

  • 길드 특성 및 아이템 시스템 설계·개발

    길드 특성은 길드 전용 재화를 소비해 노드 그래프에서 특성을 해금하고, 완료되면 길드원 전체에게 버프를 부여하는 시스템입니다. 노드 폐쇄 시 나머지 노드가 시작점에 도달할 수 있는지 BFS로 검증하고, 대기시간은 데이터로 조정 가능하게 하되 재화를 소비해 단축할 수 있도록 했습니다. 특성 데이터는 상위 계층 서버에서 관리하되 실제 버프는 플레이 서버에 적용하며 변경된 버프만 전파하도록 설계했습니다. 아이템은 마법 부여 슬롯 확장 시 구조체·저장 프로시저 파라미터·인벤토리·창고·거래소·아이템 이동·패킷·UI·로그로 분산된 변경 범위를 전수 파악해 수정했고, 아이템 복구권은 파괴 이력을 최초 1회만 DB에서 로드해 메모리 캐싱하도록 구현했습니다.

  • 운영툴 개발 및 라이브 데이터 대응

    운영툴이 없는 상태에서 초기 구축부터 참여해 메인 개발자 3명 중 1명으로 운영 기능 전반을 개발했고, 담당 기능은 툴 화면부터 백엔드, 연동되는 게임 서버 로직까지 한 사람이 끝까지 처리했습니다. 여러 환경을 하나의 툴에서 실시간 전환 관리하며, 요청받은 기능 구현에 그치지 않고 거래소 등록 아이템 차단·인게임 아이템 사용 금지 등 운영 리스크 차단 기능을 직접 제안·개발했습니다. 부정 획득·비귀속 지급·환불 등 민감한 데이터 이슈에서는 연관 테이블 전체를 파악해 보정 쿼리를 직접 작성했습니다.

  • 운영툴 다국어 전환 성능 개선

    운영툴 다국어는 툴을 띄울 때 모든 페이지의 언어를 한꺼번에 변경하는 방식이었습니다. 관리 권역이 늘어나면서 국가를 전환할 때마다 적용 시간이 길어져 운영자가 대기하게 됐습니다. 전체 일괄 적용을 화면에 표시되는 페이지만 그 시점에 변경하는 방식으로 바꿔 전환 지연을 없앴습니다.

  • 글로벌 런칭 대응 및 서버 통합(DB 병합)

    서버 콘텐츠와 운영툴 영역의 글로벌 런칭 대응을 담당해 우편·점검·공지·이벤트 등 DB에 저장되는 문자열 콘텐츠를 전수 조사하고 다국어를 적용했습니다. 서로 다른 서버의 별개 DB를 하나로 합치는 서버 통합 작업에서 테이블 단위 병합 방식과 식별자 충돌 처리, 콘텐츠 관점의 병합 기준을 함께 설계했습니다. 이 외에 유저 언어 코드 캐싱, 카카오 SDK 3.0·4.0 대응, 로그 영문화, 운영툴 다국어 번역 추출·적용 구조를 구현했습니다.

  • CI/CD 운영 및 AI 기반 통합 관리 체계 구축

    Jenkins·Rundeck·Jira·Confluence를 API로 연동해 AI 자동화로 분석·관리하는 체계를 구성했습니다. 빌드·배포 상태 확인과 장애 원인 분석, 이슈·문서 연계를 자동화해 반복 확인에 쓰던 시간을 단축했습니다. DEV·STAGE·QA 등 여러 브랜치 환경의 설정·스케줄·에이전트 구성을 운영하며, Jenkins 콘솔 로그와 REST API 결과를 대조해 빌드 문제의 원인을 추적했습니다.

  • AI 기반 설정 변경의 안전장치 설계

    AI 에이전트가 API로 빌드 시스템 설정을 직접 수정하는 구조였기 때문에, 잘못된 변경이 빌드 환경을 훼손하지 않도록 변경 규칙을 직접 설계해 적용했습니다. 변경 전 최신 상태를 다시 확인해 오래된 기준으로 덮어쓰는 것을 막고, 다른 경로에서 발생한 동시 변경을 감지하도록 했습니다. 변경 내역을 검토할 때 민감 정보가 노출되지 않게 처리했고, 백업 후 적용해 실패 시 자동 롤백되도록 구성했으며 모든 변경에 감사 기록을 남겼습니다. AI에 쓰기 권한을 주면서도 빌드 환경의 안전성을 지키는 것이 목표였습니다.

문제
길드 콘텐츠는 Zone에서 개인 재화를 선차감한 뒤 World 처리가 항상 성공한다고 가정해, 길드 재화 검증 실패 시 개인 재화만 차감된 상태가 남을 수 있었습니다. 일일 출석 보상은 Zone 처리 후 World에 DB 저장을 요청하는 순서여서 비동기 처리 중 동일 요청이 연속 유입되면 중복 지급이 가능했습니다.
역할
두 사례 모두 서버 간 처리 순서와 실패 복구 구조를 직접 재설계했습니다.
해결
World 처리 결과를 Zone으로 반환하도록 확장하고 실패 시 저장된 기존 Task를 롤백해 선차감 개인 재화를 복구하는 보상 트랜잭션을 구현했습니다. 출석 보상은 처리 순서를 역전시켜 계정 데이터를 관리하는 World가 메모리 카운트로 중복 요청을 먼저 차단하고, DB 저장 성공을 확인한 요청만 Zone에 통보해 보상을 반영하도록 변경했습니다.
결과

결과

상황
아키에이지 워 글로벌 런칭 대응 담당. DB에 저장되는 문자열 콘텐츠를 전수 조사해 다국어를 적용하는 작업을 수행했습니다.
문제
기존 구조는 서버가 유저 정보를 캐싱해 보낸이·제목·내용을 언어별 번역 텍스트로 저장했습니다. 그런데 유저 언어 정보는 계정 DB에만 존재해, 미접속 유저에게 우편을 발급해야 하는 경우 지급 자체가 불가능했습니다. 신규 언어 추가 시 서버 데이터를 재구성해야 하는 부담도 있었습니다.

해결
보상 우편에는 번역 텍스트 대신 CMS 키만 저장하고 번역은 클라이언트가 자신의 언어로 수행하도록 책임을 이전했습니다. 앞서 진행한 우편 시스템 전면 리팩토링으로 타입·책임을 분리해 둔 구조 위에 신규 타입을 추가하는 형태로 적용했습니다.
결과
